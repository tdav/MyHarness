## 1. Краткое резюме (TL;DR)

**Vue 3** и **htmx** — это не конкуренты в классическом смысле, а инструменты, основанные на принципиально разных философиях:

| Аспект | Vue 3 | htmx |
|--------|-------|------|
| **Парадигма** | SPA-фреймворк (клиентский рендеринг, реактивность) | Hypermedia-расширение HTML (серверный рендеринг) |
| **Язык взаимодействия с сервером** | JSON API | HTML (hypermedia) |
| **Состояние** | Клиентское (реактивные proxy-объекты) | Серверное (HATEOAS) |
| **Build step** | Обязателен для production (Vite) | Не нужен |
| **Размер (gzip)** | ~48.6 kB (полный экспорт) | ~18.2 kB |
| **Компонентная модель** | Да (SFC, Composition API) | Нет (серверные шаблоны) |
| **Лучше для** | Сложных интерактивных UI, SPA, PWA | CRUD-приложений, контентных сайтов, админок |

**Главный вывод:** выбор зависит от характера приложения. Vue 3 даёт богатую клиентскую интерактивность и компонентную архитектуру ценой сложности экосистемы. htmx возвращает простоту классического веба, делая сервер главным источником истины, и радикально сокращает количество JS-кода.

## 2. Философия и архитектурный подход

### Vue 3: «Прогрессивный фреймворк»

Vue позиционируется как **«The Progressive Framework»** — фреймворк, который растёт вместе с потребностями. Он построен на двух столпах:

- **Декларативный рендеринг** — шаблонный синтаксис расширяет HTML, позволяя декларативно описывать вывод на основе JavaScript-состояния.
- **Реактивность** — Vue автоматически отслеживает изменения состояния и эффективно обновляет DOM.

Vue может использоваться по-разному: от простого улучшения статического HTML до полноценного SPA, SSR, SSG, десктоп- и мобильных приложений. Это **клиентско-ориентированная** модель: состояние живёт в браузере, сервер предоставляет JSON API.

> Источник: [vuejs.org/guide/introduction](https://vuejs.org/guide/introduction.html)

### htmx: «Hypermedia-Driven Application»

htmx — это библиотека, которая **расширяет HTML как гипермедиа**, позволяя обращаться к современным возможностям браузера напрямую из HTML, а не через JavaScript. Философия htmx:

- **HTML — это язык приложения**, а не просто разметка. Сервер отвечает HTML, а не JSON.
- **HATEOAS** (Hypermedia As The Engine Of Application State) — состояние приложения управляется через гипермедиа.
- **Locality of Behavior (LoB)** — поведение элемента должно быть очевидно при взгляде на сам элемент (`<button hx-get="/clicked">` — понятно, что произойдёт).
- **HDA (Hypermedia-Driven Application)** — синтез MPA (простота) и SPA (лучший UX), но без JSON API и без тяжёлого клиентского состояния.

htmx обобщает идею HTML-якорей: любой элемент (не только `<a>`) может делать HTTP-запросы, любое событие (не только click) может их триггерить, любой HTTP-метод доступен, и любой элемент может быть целью обновления.

> Источник: [htmx.org/docs](https://htmx.org/docs/), [htmx.org/essays/hypermedia-driven-applications](https://htmx.org/essays/hypermedia-driven-applications/)

### Принципиальное различие

```
Vue 3:    Браузер ← JSON → Сервер (клиент рендерит HTML из данных)
htmx:     Браузер ← HTML → Сервер (сервер рендерит HTML, браузер его вставляет)
```

Это фундаментальное архитектурное различие определяет все остальные отличия.

## 3. Vue 3: подробный обзор

### Composition API

Главное нововведение Vue 3 — **Composition API**, набор функций для создания компонентов через импортируемые API вместо опций:

```vue
<script setup>
import { ref, onMounted } from 'vue'

const count = ref(0)

function increment() {
  count.value++
}

onMounted(() => {
  console.log(`Initial count: ${count.value}`)
})
</script>

<template>
  <button @click="increment">Count is: {{ count }}</button>
</template>
```

**Преимущества Composition API** (по официальному FAQ):

1. **Лучшее переиспользование логики** — Composable-функции решают все проблемы mixins. Дало рождение проектам вроде **VueUse** (огромная коллекция утилит).
2. **Более гибкая организация кода** — логика, относящаяся к одной задаче, группируется вместе, а не разбросана по `data()`, `methods`, `mounted` и т.д.
3. **Лучшая типизация (TypeScript)** — Composition API использует обычные переменные и функции, которые естественно дружелюбны к типам. Не нужны сложные type gymnastics, как в Options API.
4. **Меньший production-бандл** — шаблон в `<script setup>` компилируется в функцию в той же области видимости, без proxy-доступа через `this`, что даёт лучшую минификацию.

> Источник: [vuejs.org/guide/extras/composition-api-faq](https://vuejs.org/guide/extras/composition-api-faq.html)

### Сравнение с React Hooks

Vue явно позиционирует Composition API как улучшенную альтернативу React Hooks:

- `setup()` / `<script setup>` вызывается **один раз** (а не при каждом рендере, как React Hooks).
- Нет проблемы «устаревших замыканий» (stale closures).
- Нет чувствительности к порядку вызовов; вызовы могут быть условными.
- Vue автоматически собирает реактивные зависимости — не нужно вручную указывать массивы зависимостей (`useMemo`, `useCallback`, `useEffect`).
- Не нужно вручную кэшировать callback-функции — мелкозернистая реактивность Vue обновляет дочерние компоненты только когда нужно.

> Источник: [vuejs.org/guide/extras/composition-api-faq](https://vuejs.org/guide/extras/composition-api-faq.html) — раздел «Comparison with React Hooks»

### Реактивность

Vue 3 использует **Proxy-based** реактивность (вместо `Object.defineProperty` во Vue 2):
- `ref()` — реактивная ссылка на любое значение
- `reactive()` — реактивный объект
- `computed()` — вычисляемые свойства с автоматическим отслеживанием зависимостей
- `watch()` / `watchEffect()` — наблюдатели
- `shallowRef()` / `shallowReactive()` — escape hatch для больших структур (отключение глубокой реактивности)

### Single-File Components (SFC)

Формат `.vue` инкапсулирует логику (JS), шаблон (HTML) и стили (CSS) в одном файле. Это определяющая фича Vue и рекомендуемый способ создания компонентов при наличии build-шага.

### Экосистема

| Инструмент | Назначение |
|------------|------------|
| **Vite** | Сборщик и dev-сервер (на базе Rollup + esbuild) |
| **Vue Router** | Официальный роутер для SPA |
| **Pinia** | Официальный state management (пришёл на смену Vuex) |
| **VueUse** | Коллекция composable-утилит |
| **Nuxt 3** | Fullstack meta-фреймворк (SSR, SSG, file-based routing) |
| **Vue DevTools** | Браузерное расширение для отладки |
| **Volar** | Официальное расширение VS Code (TypeScript-поддержка) |

### Производительность Vue 3

Из официального руководства по производительности:

- **Tree-shaking**: неиспользуемые API (например, `<Transition>`) не попадают в бандл.
- **Предкомпиляция шаблонов**: при build-шаге шаблоны компилируются заранее — не нужно отправлять компилятор Vue в браузер (экономит ~14 kB gzip).
- **Code splitting**: динамические `import()` + `defineAsyncComponent` для ленивой загрузки.
- **Виртуализация списков**: `vue-virtual-scroller` для больших списков.
- **`v-memo` / `v-once`**: пропуск обновлений поддеревьев.
- **Computed stability** (Vue 3.4+): computed вызывает эффекты только при реальном изменении значения.
- **Архитектурный совет**: для чувствительной к load-производительности страницы избегать чистого CSR (client-side rendering), использовать SSR/SSG.

> Источник: [vuejs.org/guide/best-practices/performance](https://vuejs.org/guide/best-practices/performance.html)

### petite-vue

Для progressive enhancement без build-шага Vue предлагает **petite-vue** — всего **6 kB**, подмножество Vue для лёгкого улучшения статического HTML.

## 4. htmx: подробный обзор

### Как это работает

htmx добавляет HTML-атрибуты для AJAX-запросов напрямую из разметки:

```html
<button hx-post="/clicked"
        hx-trigger="click"
        hx-target="#parent-div"
        hx-swap="outerHTML">
  Click Me!
</button>
```

Это говорит htmx: «при клике отправь POST на `/clicked` и замени элемент `#parent-div` ответом».

### Ключевые атрибуты

| Атрибут | Описание |
|---------|----------|
| `hx-get/post/put/patch/delete` | HTTP-запрос к URL |
| `hx-trigger` | Событие, запускающее запрос (click, change, keyup, mouseenter, load, revealed, intersect, every 2s...) |
| `hx-target` | CSS-селектор цели обновления (поддерживает `this`, `closest`, `next`, `previous`, `find`) |
| `hx-swap` | Способ вставки: innerHTML, outerHTML, beforebegin, afterbegin, beforeend, afterend, delete, none |
| `hx-vals` / `hx-vars` | Дополнительные параметры запроса |
| `hx-include` | Включить значения других элементов |
| `hx-confirm` | Диалог подтверждения |
| `hx-boost` | Превращает ссылки и формы в AJAX-запросы (progressive enhancement) |
| `hx-sync` | Синхронизация запросов между элементами |
| `hx-preserve` | Сохранить элемент при swap (например, видео-плеер) |
| `hx-swap-oob` | Out-of-band swap — обновление элементов вне основной цели |
| `hx-select` | Выбор подмножества ответа для swap |

### Trigger-модификаторы

- `changed` — только если значение изменилось
- `delay:500ms` — задержка с сбросом таймера (для active search)
- `throttle:1s` — троттлинг
- `from:<selector>` — слушать событие на другом элементе
- `once` — только один раз

### Расширенные возможности

- **Polling**: `hx-trigger="every 2s"` (остановка кодом 286)
- **Load polling**: самозаменяющийся элемент для прогресс-баров
- **WebSockets и SSE**: через расширения
- **View Transitions API**: анимированные переходы между DOM-состояниями
- **Morph swaps**: Idiomorph, morphdom, alpine-morph — интеллектуальное слияние DOM (сохраняет фокус, состояние видео)
- **CSS Transitions**: автоматическое применение CSS-переходов при swap (нужно сохранить `id` элемента)
- **Out of Band Swaps**: обновление нескольких областей одним ответом
- **History API**: интеграция с историей браузера
- **Progressive Enhancement**: `hx-boost` деградирует до обычных ссылок без JS

### Установка

```html
<script src="https://cdn.jsdelivr.net/npm/htmx.org@2.0.10/dist/htmx.min.js"></script>
```

**Без build-шага, без npm, без зависимостей.** Можно просто скопировать файл в проект.

### Скриптинг в htmx

htmx не запрещает JavaScript, но рекомендует встраивать его в HTML (Locality of Behavior):
- **hyperscript** — `on click toggle .red-border`
- **Alpine.js** — `@click="open = !open"`
- **VanillaJS** — `onclick="this.classList.toggle('red-border')"`

> Источник: [htmx.org/docs](https://htmx.org/docs/)

## 5. Сравнение размеров и производительности

### Размер бандлов (точные данные bundlejs.com API)

| Метрика | Vue 3.5.40 | htmx 2.0.10 |
|---------|-----------|-------------|
| **Raw (uncompressed)** | 124 kB | 60.3 kB |
| **Gzip** | **48.6 kB** | **18.2 kB** |
| **Install size (npm)** | 5.04 MB | 884 kB |

> Источник: [deno.bundlejs.com](https://deno.bundlejs.com/?q=vue&text=true) и [deno.bundlejs.com](https://deno.bundlejs.com/?q=htmx.org&text=true), измерено в июле 2025

**Важные оговорки:**
- Размер Vue 48.6 kB — это **полный экспорт** со всеми API. С tree-shaking и предкомпиляцией шаблонов реальный production-бандл Vue-приложения может быть меньше, но типичное SPA-приложение с роутером, Pinia и UI-библиотекой легко достигает 150–300+ kB gzip.
- htmx 18.2 kB — это **вся библиотека целиком**, без зависимостей. Дополнительно нужен только серверный шаблонизатор.
- petite-vue (для progressive enhancement) — всего 6 kB, что сопоставимо с htmx по лёгкости.

### Производительность

| Аспект | Vue 3 | htmx |
|--------|-------|------|
| **First render (TTFB → FCP)** | Медленнее при чистом CSR (нужно скачать JS, выполнить, запросить данные). Улучшается через SSR/SSG (Nuxt) | Быстрее: сервер сразу отдаёт HTML, браузер рендерит |
| **Обновления UI** | Мгновенные (в памяти, без сетевого запроса) | Требуют сетевого round-trip (кроме скриптовых) |
| **Время до интерактивности** | Зависит от размера бандла | Минимальное (JS почти нет) |
| **Работа с большими данными** | Может тормозить (нужна виртуализация) | Контент рендерится на сервере; кейс Contexte показал, что htmx справляется с бóльшими датасетами, чем React |
| **Сетевой трафик** | JSON (компактный) + JS-бандл (один раз) | HTML (немного больше JSON, но без JS-бандла) |

### Кейс Contexte: количественные результаты портирования React → htmx

| Метрика | До (React) | После (htmx) | Изменение |
|---------|-----------|--------------|-----------|
| Размер кодовой базы | 21 500 LOC | 7 200 LOC | **−67%** |
| JS-зависимости | 255 | 9 | **−96%** |
| Время сборки | 40 сек | 5 сек | **−88%** |
| Time-to-interactive | 2–6 сек | 1–2 сек | **−50–60%** |
| Память браузера | 75 МБ | 45 МБ | **−46%** |
| Python-код | 500 LOC | 1 200 LOC | +140% (хорошо для Python-команды) |

> Источник: [htmx.org/essays/a-real-world-react-to-htmx-port](https://htmx.org/essays/a-real-world-react-to-htmx-port/) — David Guillot, Contexte, DjangoCon 2022

**Важная оговорка:** Contexte — контентное приложение (статьи, текст, изображения, фильтрация). Это идеальный сценарий для hypermedia. Не каждое приложение покажет такие результаты.

| **Вакансии на рынке** | Много (React > Vue, но Vue значим) | Очень мало |
| **Лучший сценарий** | Сложные интерактивные UI, SPA, PWA, real-time | CRUD, контент, админки, формы, SSR-first |

## 7. Когда выбирать Vue 3

Vue 3 — правильный выбор, когда:

1. **Сложный интерактивный UI** — множество динамических взаимозависимостей на клиенте (drag-and-drop, сложные фильтры, real-time обновления).
2. **SPA / PWA** — приложение с офлайн-режимом, push-уведомлениями, установкой на устройство.
3. **Богатая компонентная экосистема** — нужны готовые UI-библиотеки (таблицы с сортировкой, date pickers, сложные модальные окна).
4. **Командная работа с фронтенд-специалистами** — разделение на frontend/backend команды.
5. **TypeScript-first** — важна строгая типизация всего приложения.
6. **Переиспользование логики** — composables, VueUse, сложная бизнес-логика на клиенте.
7. **Нужна мультиплатформность** — один кодбейз для веба, десктопа (Electron/Tauri), мобильных (Capacitor).
8. **Real-time клиентские обновления** — чаты, коллаборативные редакторы, игры (через WebSockets + реактивность).

**Слабые стороны Vue 3 в этом контексте:**
- Сложность экосистемы (Vite, роутер, Pinia, SSR-настройка)
- Build-шаг обязателен
- Чистый CSR медленнее на first render
- Бандл растёт с зависимостями

## 8. Когда выбирать htmx

htmx — правильный выбор, когда:

1. **CRUD-приложения** — формы, списки, редактирование записей (классический Rails/Django/Laravel-стиль).
2. **Контентные приложения** — статьи, блоги, медиа, каталоги (как Contexte).
3. **Админки и внутренние инструменты** — не нужны офлайн и сложная клиентская логика.
4. **Серверный язык — основа стека** — команда сильна в Python (Django/Flask), Go, Ruby (Rails), PHP (Laravel), C# (ASP.NET) и не хочет писать много JS.
5. **Нужна простота и скорость разработки** — нет build-шага, нет npm-экосистемы, нет JS-fatigue.
6. **SEO и deep links важны** — серверный рендеринг даёт это бесплатно.
7. **Маленькая команда / fullstack-разработчики** — один человек делает и фронт, и бэк.
8. **Прогрессивное улучшение** — приложение должно работать без JS (доступность, SEO).
9. **Сокращение сложности** — «complexity budget»: меньше кода, меньше зависимостей, меньше сборки.

**Слабые стороны htmx:**
- Нет компонентной модели (нужны серверные шаблоны/фрагменты)
- Нет клиентской реактивности (каждое обновление — сетевой запрос)
- Сложно с сильно взаимозависимым UI (spreadsheet, карты, игры)
- Нет офлайн
- Мало готовых UI-компонентов
- Мало вакансий и разработчиков на рынке
- Дублирование API, если нужна отдельная JSON API для мобильного приложения

> Источник: [htmx.org/essays/when-to-use-hypermedia](https://htmx.org/essays/when-to-use-hypermedia/)

## 9. Реальные кейсы и опыт сообщества

### Contexte (DjangoCon 2022)

Самый известный кейс: SaaS-продукт, 2 года на React, портирован на Django templates + htmx за 2 месяца. Результаты: −67% кода, −96% зависимостей, −88% времени сборки, −50–60% time-to-interactive. Команда из 4 человек (2 бэк, 1 фронт, 1 fullstack) стала полностью fullstack.

- **Network Automation для Paris 2024 Olympics** — критическая инфраструктура на htmx
- **Next.js → htmx** — реальный пример портирования
- **wasm → htmx** — порт с WebAssembly
- **GitHub** — исторически использовал pjax/hypermedia-подход, частично перешёл на React

> Источник: [htmx.org/essays](https://htmx.org/essays/)

### Масштабируемость htmx

Создатель htmx анализирует масштабируемость по 5 осям:
- **Производительность**: HDAs stateless, горизонтально масштабируются, эндпоинты независимы, кэширование — всё работает.
- **Количество фич**: независимые UI-driven эндпоинты масштабируются хорошо.
- **Сложность фич**: серверные сложные фичи (AI chat) — отлично; клиентские сложные (spreadsheet) — плохо.
- **Размер команды**: работает до ~10 разработчиков; для 100+ — данных нет.

## 10. Критика и ограничения

### Критика htmx (из сатирического эссе "htmx sucks" от создателя)

Создатель htmx сам собрал основные аргументы против (в сатирической форме):

1. **Качество кода** — htmx использует `var`, не использует модули, один большой файл, загрязняет `window`.
2. **Нет build tools** — нет TypeScript, нет современных JS-фич (хотя фактически build-шаг есть через bash-скрипты).
3. **Нет компонентов** — нет аналогов MUI, Chakra, NextUI. Нужно интегрировать Web Components вручную.
4. **Нет разделения frontend/backend** — устраняет организационную модель, успешную для многих компаний.
5. **Бэкенд-разработчики делают плохой UI** — нет специализированных фронтендеров.
6. **XSS-уязбимости** — поведение в разметке требует санитизации HTML.
7. **Нет вакансий** — ~2 вакансии на Indeed против 13 758 для React.
8. **Нет разработчиков для найма** — все учат React.
9. **Дублирование API** — если нужна мобильная API, её нужно делать отдельно от HTML-эндпоинтов.
10. **Не масштабируется** — для больших приложений компонентная модель React чище.

> Источник: [htmx.org/essays/htmx-sucks](https://htmx.org/essays/htmx-sucks/) (сатирическое эссе, но аргументы реальные)

### Критика Vue 3

1. **Сложность экосистемы** — Vite, Vue Router, Pinia, Nuxt, Volar — много движущихся частей.
2. **Build-шаг обязателен** — нельзя просто подключить через `<script>` (хотя petite-vue решает это для простых случаев).
3. **Два API стиля** — Options API и Composition API могут запутать новичков.
4. **Меньше вакансий, чем React** — Vue популярен, но React доминирует на рынке.
5. **Чистый CSR медленный** — нужен SSR/SSG (Nuxt) для хорошего first render, что добавляет сложность.
6. **Реактивность имеет накладные расходы** — глубокая реактивность на больших структурах (100 000+ свойств) требует `shallowRef`.

## 11. Гибридный (Transitional) подход

Важный вывод из исследования: **это не бинарный выбор**. Термин «Transitional Applications» (Rich Harris) описывает приложения, смешивающие hypermedia и SPA-концепции.

### Практические гибридные стратегии

1. **htmx + Alpine.js** — htmx для серверных обновлений, Alpine для лёгкой клиентской интерактивности (модалки, dropdowns, tabs). Самая популярная связка в htmx-сообществе.

2. **htmx + Vue-острова** — основная страница на htmx, отдельные интерактивные виджеты на Vue (через Web Components или Micro Frontends). htmx-эссе отмечает, что встраивать SPA-компоненты в hypermedia-приложение проще, чем наоборот.

3. **Vue + htmx-подобные приёмы** — Vue-приложение с серверным рендерингом (Nuxt) для контентных страниц и клиентской реактивностью для интерактивных разделов.

4. **petite-vue + серверный рендеринг** — для лёгкого progressive enhancement без build-шага (6 kB), когда полный Vue избыточен.

> Источник: [htmx.org/essays/when-to-use-hypermedia](https://htmx.org/essays/when-to-use-hypermedia/) — раздел «Transitional Applications & Hypermedia»

## 12. Выводы

### Принципиальная разница

Vue 3 и htmx решают разные проблемы и основаны на разных архитектурных парадигмах:

- **Vue 3** — это инвестиция в **клиентскую богатую интерактивность**. Вы платите сложностью экосистемы, build-шагом и размером бандла, но получаете реактивность, компонентную модель, TypeScript, огромную экосистему UI-библиотек и возможность строить SPA/PWA/десктоп/мобайл.

- **htmx** — это инвестиция в **простоту и серверно-ориентированную архитектуру**. Вы платите отсутствием клиентской реактивности и компонентной модели, но получаете радикально меньше кода, нет build-шага, лучшее first-render, SEO из коробки, и возможность работать fullstack на одном серверном языке.

### Ключевые преимущества Vue 3 над htmx

1. ✅ **Клиентская реактивность** — мгновенные обновления без сетевых запросов
2. ✅ **Компонентная модель** — SFC, props, slots, composables для переиспользования
3. ✅ **Богатая экосистема UI-компонентов** — Vuetify, Element Plus, PrimeVue, Quasar
4. ✅ **TypeScript** — полная типизация приложения
5. ✅ **Offline / PWA** — полноценная работа без сети
6. ✅ **Сложный интерактивный UI** — drag-and-drop, real-time, игры, редакторы
7. ✅ **Рынок труда** — значительно больше вакансий и разработчиков
8. ✅ **DevTools** — отличная отладка

### Ключевые преимущества htmx над Vue 3

1. ✅ **Простота** — нет build-шага, нет npm-экосистемы, нет JS-fatigue
2. ✅ **Размер** — 18.2 kB против 48.6 kB (и без зависимостей)
3. ✅ **First-render** — серверный HTML рендерится мгновенно
4. ✅ **SEO / deep links** — из коробки, без SSR-настройки
5. ✅ **Меньше кода** — кейс Contexte: −67% LOC
6. ✅ **Fullstack-разработка** — один разработчик делает весь стек
7. ✅ **Progressive enhancement** — работает без JS
8. ✅ **Locality of Behavior** — поведение очевидно из HTML
9. ✅ **Серверный язык как основа** — Python, Go, Ruby, PHP, C# без необходимости писать много JS
10. ✅ **Независимые эндпоинты** — легче оптимизировать и кэшировать

### Рекомендация

| Если ваше приложение... | Рекомендация |
|------------------------|-------------|
| Контентное (статьи, каталоги, медиа) | **htmx** |
| CRUD / админка / внутренний инструмент | **htmx** |
| Сложный интерактивный UI с многими зависимостями | **Vue 3** |
| SPA / PWA / офлайн | **Vue 3** |
| Real-time / коллаборативный редактор | **Vue 3** |
| SEO-критичный сайт с интерактивностью | **htmx** или **Nuxt (Vue SSR)** |
| Маленькая fullstack-команда, серверный язык | **htmx** |
| Большая команда с фронтенд-специалистами | **Vue 3** |
| Мультиплатформность (веб + десктоп + мобайл) | **Vue 3** |
| Смешанное (контент + интерактивные острова) | **htmx + Alpine** или **Nuxt islands** |
